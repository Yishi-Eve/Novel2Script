# 剧本YAML Schema定义文档

## 一、概述

本文档定义了AI小说转剧本工具输出的YAML格式剧本的Schema规范。该Schema遵循中国影视剧本行业标准，旨在生成可直接阅读、编辑和进一步打磨的剧本初稿。

### 1.1 文档目的

- 定义剧本YAML文件的结构和格式规范
- 说明各字段的含义和取值范围
- 阐述Schema设计的原因和考量
- 提供示例供参考和验证

### 1.2 适用范围

- AI小说转剧本工具的输出格式
- 剧本预览和编辑功能的数据结构
- 剧本文件的存储和交换格式

---

## 二、设计原则

### 2.1 核心原则

| 原则 | 说明 | 设计原因 |
|------|------|----------|
| 剧本格式标准化 | 遵循中国影视剧本行业规范 | 确保输出的剧本符合行业标准，可直接用于影视制作流程 |
| 内容连贯性 | 场景描写和对话保持自然流畅 | 避免碎片化，提升剧本的可读性和艺术性 |
| 行文表现力 | 通过文字描写体现镜头调度 | 留给导演和摄影创作空间，不使用技术指令限制创作 |
| 易于阅读编辑 | 输出的剧本可直接阅读和修改 | 降低作者使用门槛，便于后续人工打磨 |

### 2.2 结构设计考量

**为什么使用YAML格式？**

| 考量 | 说明 |
|------|------|
| 可读性 | YAML使用缩进和简洁语法，比JSON更易阅读 |
| 可编辑性 | 作者可以直接用文本编辑器修改，无需专业工具 |
| 结构化 | 保持程序可解析性，便于后续处理 |
| 扩展性 | 支持注释，便于添加说明和备注 |

**为什么采用层级结构（script → episodes → scenes）？**

| 层级 | 作用 | 设计原因 |
|------|------|----------|
| script | 顶层容器 | 包含元数据、角色表和剧本内容，提供完整上下文 |
| episodes | 幕 | 对应小说章节，保持叙事节奏 |
| scenes | 场景 | 剧本最小叙事单元，描述连续的时空 |

## 三、Schema定义

### 3.1 完整结构

```yaml
# ============================================================
# 剧本YAML Schema v1.0
# 用于AI小说转剧本工具的输出格式
# 遵循中国影视剧本标准格式
# ============================================================

script:
  # ---- 元数据 ----
  metadata:
    title: string              # 剧本标题
    original_author: string    # 原作者
    adapter: string            # 改编者（AI/人工）
    genre: string              # 题材类型
    total_episodes: int        # 总幕数
    total_scenes: int          # 总场景数
    created_at: datetime       # 创建时间
    version: string            # Schema版本号
    synopsis: string           # 剧本简介（可选）

  # ---- 角色表 ----
  characters:
    - name: string             # 角色名称
      description: string      # 角色描述
      gender: string           # 性别（可选）
      age: string              # 年龄段（可选）
      appearance: string       # 外貌特征（可选）
      personality: string      # 性格特点（可选）
      relationship: string     # 与其他角色关系（可选）

  # ---- 剧本内容 ----
  episodes:
    - episode_number: int      # 幕序号
      title: string            # 幕标题
      summary: string          # 幕概要（可选）

      scenes:
        - scene_number: int    # 场景序号
          scene_header: string # 场景标题行
          content: string      # 场景内容
```

### 3.2 字段说明

#### 3.2.1 元数据字段（metadata）

| 字段 | 类型 | 必填 | 说明 | 设计原因 |
|------|------|------|------|----------|
| title | string | 是 | 剧本标题 | 标识剧本，便于管理和检索 |
| original_author | string | 是 | 原作者 | 保护版权，标注原著归属 |
| adapter | string | 是 | 改编者 | 标注改编来源（AI或人工） |
| genre | string | 是 | 题材类型 | 便于分类和推荐 |
| total_episodes | int | 是 | 总幕数 | 统计信息，便于了解剧本规模 |
| total_scenes | int | 是 | 总场景数 | 统计信息，用于工作量评估 |
| created_at | datetime | 是 | 创建时间 | 记录生成时间，便于版本管理 |
| version | string | 是 | Schema版本号 | 支持未来格式升级 |
| synopsis | string | 否 | 剧本简介 | 提供剧本概览，便于快速了解 |

**为什么元数据要包含这些字段？**

元数据提供了剧本的"身份证"信息，使得：
1. 作者可以快速了解剧本基本情况
2. 便于剧本的分类、检索和管理
3. 保护原著版权，明确改编来源
4. 支持后续的版本管理和协作

#### 3.2.2 角色字段（characters）

| 字段 | 类型 | 必填 | 说明 | 设计原因 |
|------|------|------|------|----------|
| name | string | 是 | 角色名称 | 角色唯一标识 |
| description | string | 是 | 角色描述 | 提供角色基本信息 |
| gender | string | 否 | 性别 | 辅助角色塑造 |
| age | string | 否 | 年龄段 | 辅助角色塑造 |
| appearance | string | 否 | 外貌特征 | 辅助视觉化想象 |
| personality | string | 否 | 性格特点 | 保持角色一致性 |
| relationship | string | 否 | 与其他角色关系 | 理清人物关系 |

**为什么角色表要单独列出？**

1. **全局视角**：角色表提供全剧角色的概览，便于作者把握人物关系
2. **一致性保障**：AI转换时参考角色表，确保角色性格前后一致
3. **便于管理**：独立于场景，便于角色信息的查看和编辑
4. **行业标准**：专业剧本通常包含角色表

#### 3.2.3 场景字段（scenes）

| 字段 | 类型 | 必填 | 说明 | 设计原因 |
|------|------|------|------|----------|
| scene_number | int | 是 | 场景序号 | 唯一标识，便于引用和定位 |
| scene_header | string | 是 | 场景标题行 | 遵循行业标准格式 |
| content | string | 是 | 场景内容 | 包含描写和对话的完整场景 |

**为什么content使用纯文本而非结构化数据？**

| 考量 | 说明 |
|------|------|
| 可读性 | 纯文本保持剧本的文学性，阅读体验更好 |
| 连贯性 | 避免碎片化，场景描写和对话自然衔接 |
| 灵活性 | 作者可以直接编辑，无需了解复杂结构 |
| 行业标准 | 传统剧本就是纯文本格式 |

## 四、格式规范

### 4.1 scene_header 格式

```
格式：地点 时间 内外景
```

| 元素 | 说明 | 示例 |
|------|------|------|
| 地点 | 具体的场景位置 | 出租屋、医院走廊、公园湖边 |
| 时间 | 场景发生的时间 | 日、夜、清晨、黄昏、傍晚、深夜、凌晨 |
| 内外景 | 室内/室外 | 内、外、内外 |

**示例：**
- `出租屋 夜 内`
- `医院走廊 日 内`
- `公园湖边 黄昏 外`
- `办公室 日 内`
- `山顶 清晨 外`
- `火车站台 雨夜 外`

**为什么采用这种格式？**

这是中国影视行业的标准格式：
1. **简洁明了**：一行包含场景的核心信息
2. **便于拍摄**：导演和场记可以快速了解场景需求
3. **行业通用**：符合国内影视制作的习惯

### 4.2 content 格式规范

#### 场景描写
使用连贯的叙述性文字，不要碎片化。

```
✅ 正确：桌上饭菜热气腾腾，李国才在客厅摆放碗筷。

❌ 错误：桌上饭菜热气腾腾。李国才在客厅。他在摆放碗筷。
```

#### 角色对话
格式：`角色名：台词内容`

```
小婉：国才，袄子全干了么？
```

#### 带动作的对话
格式：`角色名（动作描述）：台词内容`

```
易国才（盛着汤）：干了吧，这几天都出大太阳了。
```

#### 角色动作
使用叙述性文字描述。

```
易国才盛好两碗汤放在桌上。
```

#### 内心活动
通过描写自然表现，不要使用"他想"等直接表述。

```
✅ 正确：小婉愣了一下，看着手中的红棉袄。

❌ 错误：小婉想：这件衣服居然是他买的？
```

**为什么禁止使用镜头指示？**

| 原因 | 说明 |
|------|------|
| 留白创作 | 给导演和摄影留出创作空间 |
| 避免限制 | 不同导演有不同的镜头语言 |
| 保持文学性 | 剧本首先是文学作品 |
| 行业规范 | 专业编剧通常不写镜头指示 |

## 五、示例输出

### 6.1 完整示例

```yaml
script:
  # ---- 元数据 ----
  metadata:
    title: "红棉袄"
    original_author: "张三"
    adapter: "AI Assistant"
    genre: "都市情感"
    total_episodes: 1
    total_scenes: 3
    created_at: "2024-01-15T10:30:00"
    version: "1.0"
    synopsis: "一对年轻夫妻的日常生活片段，展现平凡生活中的温情"

  # ---- 角色表 ----
  characters:
    - name: "李国才"
      description: "年轻丈夫，性格幽默，体贴妻子"
      gender: "男"
      age: "28岁"
      appearance: "普通长相，穿着朴素"
      personality: "幽默、体贴、有点小聪明"
      relationship: "小婉的丈夫"

    - name: "小婉"
      description: "年轻妻子，温柔细心，善解人意"
      gender: "女"
      age: "26岁"
      appearance: "清秀，长发"
      personality: "温柔、细心、偶尔俏皮"
      relationship: "李国才的妻子"

  # ---- 剧本内容 ----
  episodes:
    - episode_number: 1
      title: "红棉袄"
      summary: "一个普通的夜晚，夫妻二人在家中闲聊，提及一件红棉袄的故事"

      scenes:
        - scene_number: 1
          scene_header: "出租屋 夜 内"
          content: |
            桌上饭菜热气腾腾，李国才在客厅摆放碗筷。卧室里，小婉拿起堆在床上的衣服，整理着。小婉拿起那件红棉袄，扭头望向客厅。

            小婉：国才，袄子全干了么？

            易国才（盛着汤）：干了吧，这几天都出大太阳了。

            小婉（捏了捏袄子袖口）：好像还有点氤氲气。

            易国才盛好两碗汤放在桌上。

            易国才：先别干了，过来喝汤吧。

            小婉捏着袄子的两个袖口走过来。

            易国才：你还真别说，前天我爸在这住了一晚。在阳台看到了这件衣服，还问我这件红衣服是谁的嘞。

            小婉（笑）：喔，那你怎么说的？

            国才（停顿了两秒）：以后告诉你。

            小婉：哟，我还不稀罕知道呢。

        - scene_number: 2
          scene_header: "出租屋 夜 内"
          content: |
            两人坐在桌前喝汤，气氛温馨。

            小婉（尝了一口汤）：今天的汤味道不错。

            易国才（得意）：那当然，我可是特意多炖了半小时。

            小婉（笑）：夸你两句就飘了。

            易国才夹了一块肉放到小婉碗里。

            易国才：多吃点，最近都瘦了。

            小婉：哪有，我还觉得自己胖了呢。

            易国才：胖点好，抱着舒服。

            小婉（嗔怪）：就知道贫嘴。

        - scene_number: 3
          scene_header: "阳台 夜 外"
          content: |
            饭后，小婉站在阳台上晾那件红棉袄。易国才走过来，从背后轻轻抱住她。

            易国才：其实那件红棉袄，是我前年给你买的生日礼物。

            小婉（愣了一下）：真的？

            易国才：嗯，那时候你还不认识我。

            小婉转过身，看着易国才。

            小婉：那你怎么不早说？

            易国才（挠头）：怕你觉得我太主动了。

            小婉（笑着靠在易国才肩上）：傻瓜。

            月光洒在两人身上，红棉袄在微风中轻轻摇曳。
```

## 七、设计原因总结

### 7.1 整体结构设计

| 设计决策 | 原因 |
|---------|------|
| 采用YAML格式 | 可读性强，便于人工编辑，同时保持结构化 |
| 三层层级结构 | script → episodes → scenes，符合剧本的叙事结构 |
| 元数据独立 | 提供剧本概览信息，便于管理和检索 |
| 角色表独立 | 全局视角，保障角色一致性 |

### 7.2 内容格式设计

| 设计决策 | 原因 |
|---------|------|
| content使用纯文本 | 保持剧本的文学性和可读性 |
| 不拆分对话/动作/旁白 | 避免碎片化，让剧本更自然流畅 |
| 不使用镜头指示 | 留给导演和摄影创作空间 |
| scene_header标准化 | 遵循影视剧本场景标题规范 |

### 7.3 角色系统设计

| 设计决策 | 原因 |
|---------|------|
| 必填+可选字段 | 核心信息必填，细节信息可选 |
| 关系字段 | 帮助理解人物关系，保持一致性 |

### 7.4 可扩展性设计

| 设计决策 | 原因 |
|---------|------|
| version字段 | 支持未来格式升级 |
| 可选字段 | 允许渐进式完善剧本 |
| YAML注释 | 支持添加说明和备注 |
